AIS performance baseline (first-order)
======================================
Date 2026-06-09. Build: c/ais -O2 (make). One desktop core, /tmp (local disk).
Reproduce: python3 tests/perf/gen.py /tmp/ais_1m 1000000
           ais -f /tmp/ais_1m -y compact      (builds idx/ from store)
           then the timings below. Generator seed 20260606 (deterministic).

Dataset
  records   1,000,000     (~ a heavy human lifetime: dozens/day x 365 x ~70 yr)
  store     85 MB, 1,000,000 lines  "id|keys|value"
  keys      4,000 distinct          (human active vocab ~10-20K => key-space BOUNDED)
  postings  1.8M total; hottest key = 270,360 ids; median key = 69 ids
  meta      1,000,000 lines  "id|epoch"  spanning 1996..2026
  off       12 MB  (id->offset index, 12 B/id); multi 0 (no add'd records)

Timings (wall, one core)
  compact  (build whole index)        7.9  s    one streaming pass, 4000 lists
  find SUBSTR (full scan)             1.64 s    875,688 hits    -- grep-class
  dump (full scan)                    1.84 s    1,000,000 lines -- cat-class
  stats (streaming, ids only)         0.04 s
  put (single, at n=1M)               0.05 s    one O(n) idempotent store scan
  timeline: awk date-range on meta    0.37 s    33,520 records in ~2007
  get rare key (19 ids)               1.02 s -> 0.009 s   (id->offset index)
  get hot key (270k ids)              hours  -> 2.2 s     (id->offset index)
  generate (Python, NOT C)            132  s    the generator is the slow part

Reading
  - single-pass reads (find/dump/stats/timeline) are I/O-bound = grep/cat class. GOOD.
  - put is 50 ms interactively (a few/day = invisible); an import batches it (item 2).
  - GET *was* the bottleneck: ais_record re-scanned the store per matched id
    (O(matches x store)). FIXED by the id->offset index "off": get is now
    O(matches) seeks -- rare 1.02s -> 9 ms, hot (270k) hours -> 2.2 s.

Root cause (get AND bulk-put)
  No way to find a record by id except scanning the store.

Fix direction (keeps plain text, no hashing, all streaming)
  1. DONE (2026-06-09): id->offset index "off" (+ "multi" for add'd records), built
     at compact, maintained by put, scan-fallback when absent/stale (see Reading
     above for the speedups). Cost: 12 MB off for 1M ids; compact +2 s. (Remaining
     time on huge gets is fopen-per-result; cache the off/store handles if a
     270k-row get must beat ~2 s.)
  2. DONE (2026-08-22): the import's value lookups are batched. feed_import
     spools a RUN of A| lines (a tmpfile, plus a fixed stack array of their value
     hashes, AIS_MERGE_BATCH deep), resolves every hash -> id in ONE store pass,
     and replays the spool through ais_put_at_k_resolved, which takes the lookup
     instead of scanning. A hash repeated inside one batch takes the scanning
     path, so the outcome is the one a put per line gives. --import of A| lines
     into an empty index, desktop: 5k 1.06 s -> 0.31 s, 20k 13.4 s -> 1.75 s.
     A single interactive put still scans: O(n), 50 ms at 1M. The edit log is
     loaded once per import and looked up by hash (16k lines against 16k edit
     facts: 1.4 s; walked per line off disk it was 12 s).
  Net: every op becomes a seek or one streaming pass = find/rsync class.

Watch
  Re-run after adding features. A constant-factor slowdown is fine; flag any op
  that degrades by an ORDER OF MAGNITUDE and look there first.
