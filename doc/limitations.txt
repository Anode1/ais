AIS limitations (for developers)
================================
Hard limits (c/common.h) and design constraints. Plain text, fixed stack
buffers, no heap in the data path (the `keys` listing is the one bounded malloc;
see ais.c). Peak memory is a function of these sizes, never of the data.

Sizes (compile-time, c/common.h)
  AIS_LINE_MAX   65536   one store line "id|ts|keys|value" -- so a single VALUE,
                         or the whole keys field, maxes near 64 KB.
  AIS_KEY_MAX      512   one encoded key (a path component / filename).
  AIS_KEYS_MAX      64   keys per record AND per query (the k-way merge width).
  AIS_PATH_MAX    4096   any built path (dir + "idx/" + prefix + key).
  AIS_OFF_WIDTH     12   "off" entry = 11-digit (offset+1): the store is capped
                         near 90 GB before offsets overflow (raise to lift it).

Value rules
  - A value is ONE line: no newline, and no '|' (the reserved field delimiter).
  - Multi-line or large text -> `ais --doc` (saved as a blob file under blobs/;
    only its relative path is stored as the value).
  - `find` searches VALUES only, not blob CONTENT -- blobs are recalled by keys.

Keys
  - Encoded = lowercase + whitespace -> '_'. Case-folding is ASCII-only, so a
    non-ASCII key (Cyrillic, etc.) must already be lowercase. UTF-8 is stored
    byte-transparently. The shard prefix is the first CHARACTER (two characters
    for an ASCII key), never a partial UTF-8 sequence: a truncated one is not a
    legal filename on APFS, so on macOS and iOS the posting could not be written
    at all and the key recalled nothing. An index that predates this and holds
    keys starting with a three- or four-byte character needs one --compact,
    which rebuilds idx/ from the store.

Concurrency / scale
  - Reads take NO lock (any number run at once). Writers take an exclusive flock
    per mutating op and reload next_id under it, so concurrent writers serialize
    safely and never collide on an id; a long-lived reader (ais --serve) does not
    block the CLI. See doc/dev/LOCKING.md.
  - Idempotent put scans the store, O(n) per put: fine interactively (~50 ms at
    1M records). An import resolves a batch of values in one pass (feed.c), so
    a bulk import is O(n^2 / 256): 20k lines in under 2 s.
  - get is O(matches) via the "off" id->offset index once `compact` has built it
    (a pre-"off" index falls back to a scan until you compact).

Files (in the index directory)
  store is the source of truth. idx/ off multi are DERIVED -- delete any of
  them and `compact` rebuilds it. blobs/ holds documents and is REAL DATA (not
  rebuildable). tomb, ktomb, katt and edits are REAL DATA too: they are the
  record of what was DELETED, detached, re-attached and EDITED, and nothing can
  rebuild them from the store, because a deleted record is not in the store.
  Removing tomb resurrects everything ever deleted -- and the next sync pushes
  those records back to every other device; removing edits lets a stale copy of
  an edited value, arriving from a backup, put the old text back. next_id is the
  id counter; lock is the writer flock. edits grows by one line per in-place
  edit, carries the replacement text, and is never pruned (--forget-deleted
  rewrites it, dropping only deleted records' facts): a record edited many
  times costs more in the edit log and in every sync bundle than in the store.
  Editing a document points its record at a fresh blob; the edit fact syncs
  even when the body does not (a body over the 64 MiB transfer cap, or a body
  whose write failed mid --import), and a peer applying the fact discards its
  old body without checking the new one arrived. Keep documents that large out
  of edits, or sync them by whole folder.
